TKAPQL

TKAPQL is a minimalistic yet complete authentication protocol. TKAPQL stands for Toki Pona Authentication Protocol and Query Language. Toki Pona is a conlang created in 2001 by @janSofia, and has under 125 words. It is so minimalistic, in fact, that banana translates to yellow stick-like fruit (yes, really!). So why not use that to solve the problems of the modern auth industry?

How TKAPQL works

TKAPQL in its essence is very simple, and you could say it has been derived from RADIUS. First of all, we make simple use of the HTTPS Authorization header, since the only thing distinguishing clients from one another is the bearer token they provide in the Authorization header. TKAPQL only utilizes one simple endpoint: /kulupu (kulupu means "group", or "collective"). Here is what the client sends to the server when asking for authentication:



  POST /kulupu HTTP/1.1
  Host: example.com
  Authorization: Bearer bearerTokenHere
  Content-Type: application/x-www-form-urlencoded
  Content-Length: something
  nimi=username
  lawa=password

You might have noticed the plaintext password. TKAPQL only allows for HTTPS, so this is safe (any use of HTTP in a TKAPQL request shall be refused by the server). You might also have noticed the key=value pairs are separated by new lines for simplicity. If the authentication fails for a simple reason, the server returns lon=ike and an HTTP code 400 (ike means bad). If the reason for failure is complicated, the server shall return lon=ike suli (suli means very) and HTTP code 500. Finally, if the authentication succeeds, the server sends back 



  lon=pona
  kulupu=accounting,admin,hr
  linja=steve@example.com

That, folks, is the entire TKAPQL spec sheet. One day, additional fields may be added, but will not be considered essential parts of TKAPQL.
